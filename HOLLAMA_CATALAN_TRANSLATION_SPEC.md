# Hollama — Catalan (ca) localization: Copilot task specification

**Project:** [`fmaclen/hollama`](https://github.com/fmaclen/hollama)  
**Target language:** Catalan  
**Locale code:** `ca`  
**Source language:** English (`en`)  
**Upstream target branch:** `fmaclen/hollama:main`  
**Workflow:** inspect and export → human translation → import and validate → pull request

> This document is intended to be added to the root of your own fork as
> `COPILOT_TRANSLATION_CA.md`, then supplied as context to GitHub Copilot.

---

## 1. Important repository facts

The repository has already implemented internationalization. **Do not create a second i18n system.** Extend the existing one.

The repository currently uses:

- SvelteKit, Svelte and TypeScript.
- [`typesafe-i18n`](https://github.com/ivanhofer/typesafe-i18n) for translations and locale loading.
- English as the base locale.
- Translation dictionaries under `src/i18n/<locale>/index.ts`.
- Generated i18n support files under `src/i18n/`.

The main files to inspect are:

| File | Purpose |
|---|---|
| `src/i18n/en/index.ts` | English source dictionary; authoritative source for translation strings |
| `src/i18n/<locale>/index.ts` | Existing dictionaries for other languages; use these as examples |
| `src/i18n/i18n-types.ts` | Generated locale and translation types; do not edit by hand |
| `src/i18n/i18n-util.ts` | Generated locale registry and utilities; do not edit by hand |
| `src/i18n/i18n-util.sync.ts` | Generated synchronous locale loader; do not edit by hand |
| `src/i18n/i18n-util.async.ts` | Generated asynchronous locale loader; do not edit by hand |
| `.typesafe-i18n.json` | Existing typesafe-i18n configuration |
| `package.json` | Scripts and dependencies |

At the time this specification was prepared, the generated locale list contained `de`, `en`, `es`, `fr`, `it`, `ja`, `ka`, `pt-br`, `tr`, `vi` and `zh-cn`. Add Catalan as `ca`; do not rename or modify existing locales.

`package.json` already defines:

- `npm run typesafe-i18n` — run the i18n generator.
- `npm run check` — Svelte/TypeScript checks.
- `npm run lint` — Prettier and ESLint checks.
- `npm run build` — production build.
- `npm test` — Playwright tests.

The `dev` script also runs the i18n generator alongside Vite. Inspect the current scripts before relying on them; do not change dependency versions merely for this task.

Existing non-English dictionaries commonly import English and spread it first, then override translated keys. This gives a safe English fallback for missing translations. Follow the current pattern used by the neighboring locale files instead of inventing a new one.

The English source dictionary contains parameterized strings. For example, it currently includes tokens such as `{model:string}`, `{hostname:string}` and `{ip:string}`. These are runtime placeholders, not ordinary words, and must be preserved exactly.

**Repository snapshot checked:** 30 October 2026. Re-check the live `main` branch before implementation because the project may have changed since this specification was written.

## 2. Working rules and safety boundaries

1. Work only in my fork of `fmaclen/hollama`, on a new feature branch. Never push directly to the upstream repository.
2. Do not merge any pull request. I will review and submit the final contribution.
3. Do not change the behavior or wording of the English interface while preparing the export, unless a confirmed user-visible string is currently hard-coded outside i18n. In that case, report it in the audit first; do not silently refactor it during the export phase.
4. Do not alter other language dictionaries.
5. Do not translate strings with AI. The Catalan wording will be supplied by a human translator in the returned export file.
6. Do not add a new runtime localization library or a new YAML dependency. Use the existing `typesafe-i18n` implementation.
7. Do not hand-edit files marked as generated by `typesafe-i18n`. Regenerate them with the project's existing command after adding the locale.
8. Do not translate product names, model names, provider names, API identifiers, code, URLs or technical parameter identifiers unless the English UI already presents them as ordinary translatable prose.
9. Keep the export as a hand-off artifact only. It must not be imported by the running application. After its translations have been imported and validated, remove the temporary export from the final application PR unless I explicitly ask to keep it.
10. Do not commit secrets, credentials, personal data, `.env` files or generated build output.

## 3. Phase A — inspect the project and create the translation export

### Goal

Produce a complete, editable file containing every current English UI translation entry, with the original English text and enough context for a human to translate it accurately into Catalan.

### Scope of the audit

Inspect the current repository, not just the files listed above.

- Read the complete English dictionary in `src/i18n/en/index.ts`.
- Inspect existing locale dictionaries to understand conventions, fallback behavior, capitalization and technical terminology. Do not copy another language's translations as the source text.
- Trace each English dictionary entry to its UI use site where possible. Record the Svelte component or source path and a concise explanation of what the text labels or communicates.
- Search the application source for additional user-visible English strings that bypass the i18n dictionary. Include UI labels, buttons, menus, tooltips, placeholders, accessibility labels, notifications, errors, empty states, dialogs and settings descriptions.
- Separate genuine user-facing copy from non-translatable content such as logs, developer comments, test fixtures, protocol/API values, model-generated output, user-authored content, example code and third-party library text.
- Do not assume every English-looking string is translatable. Record uncertain cases separately for human review.

### Required export file

Create:

`translation/ca.json`

Use strict JSON (rather than introducing a YAML parser). JSON is easy to edit in external translation tools and can be parsed by Node.js without adding a dependency. Keep a stable structure similar to this example:

```json
{
  "meta": {
    "formatVersion": 1,
    "locale": "ca",
    "language": "Catalan",
    "sourceLocale": "en",
    "sourceDictionary": "src/i18n/en/index.ts",
    "translationInstructions": "Only edit the target field in each entry."
  },
  "entries": {
    "addConnection": {
      "source": "Add connection",
      "target": "",
      "context": "Label for the action that adds a server connection.",
      "placeholders": [],
      "locations": ["src/path/to/component.svelte"]
    },
    "modelWasDownloaded": {
      "source": "{model:string} was downloaded",
      "target": "",
      "context": "Success message shown after a model download.",
      "placeholders": ["{model:string}"],
      "locations": ["src/path/to/component.svelte"]
    }
  },
  "unmanagedUiStrings": [],
  "reviewNotes": []
}
```

The example is illustrative only. Populate the actual file from the current source tree; do not limit the export to the two example entries.

### Export requirements

- Include **every key** in the current English base dictionary. Preserve the exact key names and exact English source text.
- Keep the dictionary key as the stable identifier. Do not use the English sentence as the key.
- Set every `target` to an empty string. Do not generate or suggest Catalan translations.
- Include a short, useful `context` note. Trace the key's use site rather than guessing from the English text alone. If the context cannot be established, say so explicitly.
- Include `locations` as a list of repository-relative file paths. Use an empty list only when no use site can be found.
- Include every interpolation token in `placeholders`, exactly as it appears in the English source. The source string itself must also retain those tokens.
- Preserve punctuation, embedded line breaks, quotes and formatting in the `source` value.
- Preserve the order of keys from the English dictionary where practical. Use UTF-8.
- Add any confirmed hard-coded UI strings that require localization to `unmanagedUiStrings`, with their exact English text, proposed stable key, context and source path. Do not invent translations or silently change application code in Phase A.
- Put ambiguous strings or scope questions in `reviewNotes`; do not silently discard them.
- Do not include non-user-facing strings in `entries`.
- Make the JSON valid and ensure it can be parsed with `JSON.parse`.

### Phase A deliverables

1. `translation/ca.json` containing the complete English dictionary export and the audit results.
2. A concise audit summary in the pull request description stating:
   - number of English dictionary entries exported;
   - number of confirmed additional hard-coded UI strings;
   - number of uncertain items requiring a decision;
   - any strings or areas that could not be inspected.
3. A list of files inspected and any relevant assumptions.

### Phase A must not do these things

- Do not create `src/i18n/ca/` yet.
- Do not register `ca` in the application yet.
- Do not translate any entry.
- Do not edit the generated i18n files.
- Do not update the language selector or application behavior.
- Do not open a pull request against `fmaclen/hollama` upstream.

When Phase A is complete, commit the export on the feature branch in my fork and create a **draft pull request against my fork's `main` branch**. Do not merge it. The draft PR is only a safe place to store the export while I translate it.

Suggested branch name: `copilot/catalan-translation-export`  
Suggested draft PR title: `chore(i18n): prepare Catalan translation export`

## 4. Human translation hand-off

I will download `translation/ca.json` and translate it outside GitHub.

The translator must:

- Edit only the `target` values in `entries` (and, if agreed, the target values for reviewed `unmanagedUiStrings`).
- Leave `meta`, entry keys, `source`, `context`, `placeholders` and `locations` unchanged.
- Fill every `target` with a non-empty Catalan string. If the correct Catalan UI text is intentionally identical to English, repeat the English text instead of leaving the target blank.
- Preserve every placeholder exactly, including braces, variable names and type suffixes. For example, `{model:string}` must remain exactly `{model:string}`.
- Preserve intended line breaks and any meaningful punctuation or formatting.
- Use natural, standard Catalan suitable for the Hollama interface, consistently using Catalan terminology rather than literal Spanish calques.
- Keep product and service names such as Hollama, Ollama and OpenAI unchanged. Keep technical identifiers and model parameter names where translating them would make the interface less clear.
- Avoid translating text that is displayed as user content, model output, code, URLs or protocol values.

If a translation is uncertain, add a note to `reviewNotes` with the relevant key. Do not use an empty target as a substitute for a note.

When the translation is complete, replace the export file on the same feature branch with the translated version. This can be done by editing the file in the GitHub web interface or by committing the edited file from a local clone. Do not create a new branch for Phase B.

## 5. Phase B — import the human translations and implement Catalan

### Trigger

Start this phase only after I have supplied the completed `translation/ca.json` on the feature branch.

### Validation before changing application code

Validate the returned file against the current English source dictionary:

1. The JSON parses successfully.
2. Every English base key is present exactly once in `entries`.
3. There are no unknown or renamed keys.
4. Every `target` is a non-empty string.
5. Every interpolation token in `source` is preserved exactly in `target`; no placeholder may be removed, renamed, translated or have its type suffix changed.
6. The English `source` field still exactly matches the corresponding value in `src/i18n/en/index.ts`. If the English base dictionary has changed since export, report the difference and update the export carefully rather than overwriting or guessing.
7. Check notes and unmanaged UI strings. Do not fabricate a translation for unresolved items. Report blockers instead of silently using machine translation.

If validation fails, do not implement an incomplete locale. Tell me which keys need attention and why.

### Implementation

After validation passes:

1. Create `src/i18n/ca/index.ts` using the same structure and fallback pattern as current locale files. Use the human-provided `target` text for Catalan values.
2. Use the English dictionary as the fallback for any future keys that are not yet translated, following the repository's existing convention. Do not use the temporary JSON as a runtime dictionary.
3. Add Catalan using locale code `ca` through the project's supported `typesafe-i18n` configuration and generation workflow.
4. Run `npm run typesafe-i18n` and inspect the generated diff. This should update the generated locale/type and loader files as needed. Do not manually patch generated files unless the generator itself demonstrably fails; report that failure instead.
5. Inspect the language selector and locale-detection/persistence code. Ensure Catalan appears as **Català**, can be selected by the user, loads correctly, and remains selected according to the application's existing preference behavior.
6. If Phase A identified confirmed hard-coded UI strings, migrate only those agreed strings into the existing i18n dictionary, give them stable English keys in the base dictionary, add their human-reviewed Catalan translations, and regenerate types. Do not refactor ambiguous strings without asking me.
7. Do not change existing English wording or other locale translations as part of this task.
8. Remove the temporary `translation/ca.json` hand-off file from the final application changes after all values have been imported and validated, unless I explicitly request that it remain in the repository.
9. Do not make unrelated refactors or dependency upgrades.

### Tests and verification

Run the relevant checks using the scripts that exist in the current `package.json`:

```bash
npm run typesafe-i18n
npm run check
npm run lint
npm run build
npm test
```

Run all checks that are practical in the agent environment. Report any test that could not run and the reason. Do not claim a test passed unless it actually completed successfully.

Also verify the following manually or with appropriate automated tests:

- `ca` is present in the generated `Locales` type and locale registry.
- Both synchronous and asynchronous locale-loading paths can load Catalan.
- The language selector shows `Català` and lets the user select it.
- The selected language is retained using the same behavior as other locales.
- The Catalan UI displays translated values for the exported keys.
- No interpolation token is missing or changed.
- There are no unintended English strings in the Catalan UI, apart from intentionally retained technical/product names or explicitly documented fallback cases.
- Other languages and the English default still work.
- No unrelated files or changes are included.

### Phase B deliverables

- A complete Catalan dictionary at `src/i18n/ca/index.ts`.
- Correctly regenerated `typesafe-i18n` files and locale registration.
- A working Catalan option in the interface.
- A concise summary of files changed, validation performed and test results.
- Updated commits on the **same feature branch and draft PR in my fork**.

Suggested final PR title: `feat(i18n): add Catalan (ca) translation`

Do not merge the PR or push directly to `fmaclen/hollama`.

Paste this into the Copilot task prompt after selecting **my fork** (not `fmaclen/hollama`) and base branch `main`:

```text
Read COPILOT_TRANSLATION_CA.md in the repository root and follow it exactly.

Perform Phase A only: inspect the current Hollama repository, audit all user-facing UI text, and create the complete human-translation export at translation/ca.json. Use the current English dictionary as the source of truth, trace each key to its UI context, preserve placeholders, and report any confirmed hard-coded UI strings outside the i18n system.

Do not translate anything. Do not implement Catalan in the application yet. Do not create src/i18n/ca or edit generated i18n files. Do not change other languages or application behavior.

Commit the export and audit summary on a new feature branch in this fork, then open a DRAFT pull request against this fork's main branch. Do not create a pull request against fmaclen/hollama upstream and do not merge anything. In your final response, give me the branch name, draft PR URL, export file path, number of entries, audit findings, and any unresolved questions.
```

### Prompt B — after I return the translated export

On the draft PR for the same branch, add a normal comment mentioning `@copilot` and paste:

```text
@copilot Read COPILOT_TRANSLATION_CA.md and perform Phase B only.

The human-translated translation/ca.json is now present on this PR branch. Validate it completely against src/i18n/en/index.ts before editing application code. Do not use machine translation. If any target is empty, any key is missing/unknown, the English source has changed, or any placeholder differs, stop and report the exact problems instead of guessing.

If validation passes, implement Catalan (locale code ca) by extending the existing typesafe-i18n setup. Follow the current locale dictionary/fallback pattern, run npm run typesafe-i18n, inspect generated changes, make Català available in the language selector, and verify locale loading and persistence. Do not edit other languages or make unrelated changes. Run the repository checks listed in COPILOT_TRANSLATION_CA.md and report actual results.

Remove the temporary translation/ca.json hand-off file from the final application changes once imported, unless the repository instructions or I explicitly say otherwise. Commit the implementation to this same PR branch and update this PR. Do not merge it and do not push to fmaclen/hollama upstream.
```

GitHub's Copilot agent can be asked to revise an existing pull request by mentioning `@copilot` in a normal PR comment; by default, it pushes its changes to that PR branch. If the GitHub UI presents a model picker for the comment, select an available model before submitting.

## 7. Beginner-friendly GitHub workflow

1. Sign in to GitHub and open [the Hollama repository](https://github.com/fmaclen/hollama).
2. Click **Fork** and create a fork under your own GitHub account. This is a one-time manual step; do not ask Copilot to fork the upstream project.
3. In your fork, add this file at the repository root with the name `COPILOT_TRANSLATION_CA.md` and commit it to your fork's `main` branch.
4. Open the **Agents** area or GitHub's Copilot task prompt. Select your fork as the repository and `main` as the base branch. Do not select the maintainer's upstream repository.
5. Paste **Prompt A** above. Review the agent's summary and its draft PR. Download `translation/ca.json` and translate it outside GitHub.
6. Put the completed JSON back on the same PR branch, replacing the original export. Check that it remains valid JSON and that every `target` is filled.
7. Add a normal PR comment with **Prompt B**. Copilot should update the existing PR branch. Review the resulting diff and test report.
8. When the work is ready, open a pull request from your fork to the original repository. On GitHub's PR creation page, choose **compare across forks** and set:
   - **Base repository:** `fmaclen/hollama`
   - **Base branch:** `main`
   - **Head repository:** your fork (your GitHub username / `hollama`)
   - **Compare branch:** the feature branch used by Copilot
9. Review the final upstream pull request description and diff, then submit it. The Hollama maintainers decide whether and when to merge it.

### Access and plan note

GitHub documents Copilot cloud agent as available on paid Copilot plans, subject to repository/account restrictions and policy settings. If you cannot see the Agents task entry point or Copilot as an available agent, check your Copilot plan and whether the feature is enabled for the repository/account. You can also use Copilot in an IDE with a local clone of your fork, but the branch and pull request steps will then be done through Git/GitHub rather than the cloud agent.

## 8. Acceptance criteria

The task is complete only when all of the following are true:

- [ ] The translation export contains all current English base dictionary keys and accurate context.
- [ ] Confirmed out-of-dictionary UI strings have been reported and resolved or explicitly documented.
- [ ] All Catalan translations are human-supplied and non-empty.
- [ ] Every interpolation placeholder is preserved exactly.
- [ ] Catalan is registered as locale `ca` through the existing `typesafe-i18n` workflow.
- [ ] `src/i18n/ca/index.ts` follows the existing locale convention and English fallback behavior.
- [ ] The generated locale loaders/types include Catalan.
- [ ] `Català` is selectable in the app and persists correctly.
- [ ] Relevant checks have been run and their actual results reported.
- [ ] Existing locales and the English default continue to work.
- [ ] No unrelated changes are included.
- [ ] The completed changes are in a reviewable PR from the user's fork to `fmaclen/hollama:main`; no direct push or merge to upstream was attempted.
